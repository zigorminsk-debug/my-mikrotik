# Проверка получения данных устройства и применения конфигурации

Повод: пользователь указал hAP ac3 по корпусу, но на скриншоте приложение
показало CHR VMware, x86_64, Intel, RouterOS 7.23.2; применение завершилось
`can not run on slave interface`. Исходные ответы этого устройства пока не
получены, поэтому ни ошибка определения модели, ни подключение к другому узлу
не доказаны. Предыдущий RB951G-2HnD отображался корректно.

## Источники данных

- Имя устройства — `/system identity` поле `name`; для совместимости используется
  старый запасной вариант `identity`.
- Модель для отображения, архитектура, CPU и RouterOS — `/system resource` поля
  `board-name`, `architecture-name`, `cpu`, `version`. Данные не определяются
  по корпусу, имени интерфейса или заранее заданной таблице моделей.
- `/system routerboard` поле `model` — отдельное значение «Модель RouterBOARD»;
  `board` оставлено как запасное поле. Current/factory/upgrade firmware —
  версии RouterBOOT, а не версия ОС RouterOS. На CHR этой информации может не
  быть. Если ресурс или версия недоступны, подключение считается неуспешным.
- Пакеты читаются из `/system package`; выключенные не учитываются как
  доступные. Интерфейсы и участники bridge читаются из `/interface` и
  `/interface bridge port` одним протоколом на одном подключении. При ошибке
  чтения портов bridge конструктор не должен строить конфигурацию. Disabled
  bridge ports тоже рассматриваются как члены, поскольку их могут включить.
- API, REST и MAC-Telnet идут разными транспортами. Конструктор после чтения
  устройства использует фактически выбранный транспорт, а не повторяет поиск
  `auto` на каждом действии. Приложение не может гарантировать физическую
  идентичность роутера, если адрес переназначен или трафик перенаправлен.

## Исправленные риски

- Изменение полей подключения сбрасывает предыдущие данные и скрипт; ответы
  асинхронных запросов старого устройства не должны переиспользоваться. При
  новом подключении разделы выключены, интерфейсы выбираются заново.
- При единственном включённом bridge он предлагается для LAN/DHCP вместо
  `ether2`. Выбор порта bridge для LAN-адреса, DHCP-сервера или WAN блокируется;
  программа не удаляет порты из bridge и не переносит существующие настройки.
- Если запуск скрипта через API уже был предпринят и вернул ошибку, повторный
  запуск с другим параметром или через REST запрещён: первая попытка могла
  применить часть команд. Ошибка в UI предупреждает об этом. REST создание
  скрипта использует PUT вместо POST. В MAC-Telnet ошибки терминала и отсутствие
  подтверждённого приглашения не считаются успешным выполнением; эта проверка
  зависит от формата вывода и требует стендового теста.

## Неизвестное и границы

Эти изменения не доказывают причину сообщения `slave interface` на устройстве
пользователя. Bridge — лишь одна возможная разновидность подчинения; проверка
не охватывает все виды master/slave, bonding, VLAN и т. п. Приложение не читает
весь текущий конфиг и не проверяет автоматически конфликт существующих
IP-адресов и DHCP-серверов, внешних скриптов и правил маршрутизации. Выбор
единственного bridge — предположение, а не определение его роли. Нужны backup,
ручной просмотр, локальный доступ и испытания на целевом оборудовании.

Для разбирательства конкретного случая нужны `/system resource print`,
`/system routerboard print` (серийный номер скрыть),
`/interface bridge port print detail`, `/ip dhcp-client print detail` и
соответствующие обезличенные части сгенерированного скрипта. До этого нельзя
повторно применять частично выполнившуюся конфигурацию.

Проверки выполняются на моках API/REST, Go unit tests и проверках UI; они не
заменяют тестов RouterOS и работы четырёх различных реальных моделей. Сбои
переключения LTE, показанные в отдельном протоколе, не диагностированы.
