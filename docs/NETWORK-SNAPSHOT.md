# Снимок каналов и маршрутов — версия 0.2.5

## Для чего нужен

Снимок показывает сведения RouterOS о сетевых интерфейсах, IPv4-адресах,
DHCP-клиентах, маршрутах и отдельных служебных записях контроллера failover.
Его цель — помочь разобраться с состоянием каналов, в том числе с ранее
наблюдавшимся расхождением маршрута и состояния контроллера. Это диагностический
инструмент, а не исправление или доказательство причины переключений LTE.

## Как получить

1. Подключитесь к роутеру по IP через **RouterOS API или REST**. После успешного
   подключения вернитесь на вкладку **«Информация»**.
2. В разделе **«Снимок каналов и маршрутов»** нажмите **«Собрать снимок»**.
   Программа повторно подключится тем же фактически выбранным транспортом.
   По MAC-Telnet этот снимок пока недоступен: потребуется подключение по IP.
3. Дождитесь окончания. Посмотрите статусы разделов и значения. Повторный сбор
   выполняется только вручную. Используйте «Скопировать» или «Скачать .txt»;
   имя файла одинаково, при сборе нескольких устройств переименуйте файлы.
4. Отчёт содержит IP-адреса, шлюзы, названия интерфейсов, таблицы и комментарии
   маршрутов — они могут быть частной информацией. Проверьте текст до передачи,
   скройте при необходимости. Адрес подключения, логин и пароль специально не
   добавляются, но значения на роутере произвольны, поэтому полное отсутствие
   секретов гарантировать нельзя. В файл не включаются все поля, полученные с
   роутера, только перечисленные ниже.

При изменении любого параметра подключения снимок сбрасывается; запоздавший
ответ старого запроса не должен появиться на экране. При повторном подключении
он также очищается. Перед сбором программа повторно сравнивает имя identity
(если оно было получено), версию RouterOS, архитектуру (если получена) и исходный
`board-name` с предыдущим подключением; при расхождении сбор прерывается. Это
только проверка согласованности, а не подтверждение физической идентичности:
значения могут совпадать на разных устройствах, а REST-запросы идут отдельно.

## Данные и команды

Никаких `set`, `add`, `remove`, ping или переключений не выполняется. API
использует команды `print`, REST — HTTP GET. Сведения о разделах читаются
последовательно, а не атомарно; время начала и конца сбора указано в UTC. При
изменении маршрутов в процессе данные разных разделов могут не совпасть.

| Раздел | Источник RouterOS | Отбираемые поля |
|---|---|---|
| Интерфейсы | `/interface` | name, type, running, disabled |
| IPv4 | `/ip address` | address, network, interface, actual-interface, dynamic, disabled, invalid |
| DHCP | `/ip dhcp-client` | interface, status, address, gateway, add-default-route, default-route-distance, disabled, dynamic |
| Маршруты | `/ip route` | dst-address, gateway, immediate-gw, routing-table, routing-mark, distance, active, dynamic, disabled, unreachable, blackhole, comment |
| Планировщик | `/system scheduler` | только name `mti-failover`: name, disabled, interval, run-count, next-run |
| Переменные | `/system script environment` | только name/value глобальных mtiFailBackup, mtiFailRouteGw, mtiFailRouteDist, mtiFailProbeGw, mtiFailNoGw |

Маршруты ограничены IPv4 `0.0.0.0/0` и меткой `mti-probe-link`. Записи без
`dst-address` также показаны, поскольку нельзя надёжно установить назначение.
Другие маршруты, IPv6, маршрутизационные правила, mangle, NAT, состояние
connection tracking и внешний доступ к интернету не проверяются. Активный
маршрут сам по себе не доказывает, каким путём идёт каждый пакет или что интернет
работает. Переменные могут отсутствовать, быть устаревшими или относиться к
другому контексту; пустой список не доказывает, что контроллер выключен.

Успешный пустой раздел — «записей не найдено». Ошибка чтения показана отдельно;
она может быть связана с правами, версией RouterOS, отсутствием меню или связью.
Для API после ошибки чтения остальные разделы помечаются «не прочитано», чтобы
не полагаться на возможную рассинхронизацию соединения. REST продолжает
независимые запросы. Неполученное поле отмечается `—`, а не приравнивается к
`false`. В каждом разделе после фильтрации возвращается максимум 500 записей,
при превышении выводится предупреждение; общие лимиты клиентских ответов также
могут привести к ошибке чтения на очень больших конфигурациях.

## Проверки и границы

Проверяются API/REST моки, последовательность только читающих команд,
расхождение identity, отдельные ошибки, фильтры, лимит и реакция интерфейса на
устаревший ответ. Получение доступных полей и поведение на RouterOS 6/7, LTE и
четырёх реальных моделях ещё не подтверждены. Тесты не заменяют испытаний с
реальным устройством. Переключение каналов по-прежнему требует отдельного
разбирательства; автоматическое управление этим инструментом не запускается.
