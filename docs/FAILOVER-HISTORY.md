# История контроллера failover — 0.2.12

## Назначение и порядок использования

Это первая часть пункта «LTE и история контроллера» в плане. Она показывает
некоторые события **уже работающего** скрипта `mti-failover`, не устанавливает
причину обрыва и ничего не меняет в роутере. На реальном RouterOS эта версия не
проверялась. Показатели LTE добавлены отдельной подзадачей 0.2.13;
подробности в `LTE-DIAGNOSTICS.md`.
Дальнейшую диагностику клиентского трафика программа не запускает.

1. Подключитесь по IP по API или REST; перейдите в «Информация».
2. В разделе снимка каналов отметьте **«Добавить в снимок краткую историю
   контроллера mti-failover»** и нажмите **«Собрать снимок»**. Без отметки журнал
   не запрашивается. MAC-Telnet для этого снимка пока не поддерживается.
3. Результат можно скопировать или скачать с остальным снимком в .txt. При
   изменении отметки или подключения готовый снимок очищается; ответ старого
   запроса не показывается. Повторный сбор запускается вручную.

В отчёте доступны фиксированные категории: сообщение контроллера о переключении,
его периодическое состояние, ответ или отсутствие ответа контрольной пробы,
создание/обновление маршрута, повторная попытка и распознаваемые ошибки.
`backup` — сообщение скрипта о его состоянии, а не доказательство, что весь
трафик шёл через резерв. Поля `distance`, `expected-distance`, ответы и количество
маршрутов отражают лишь содержание сообщения. В периодическом статусе скрипт
выбирает только первый активный шлюз; мы не экспортируем этот шлюз и не делаем
вывода о маршруте пользовательского трафика.

## Источник, ограничения и конфиденциальность

- Проверка данных устройства и последующее чтение выполняются как для обычного
  снимка: выбранный API/REST, `print`/GET для истории, без повторов через другие
  протоколы. При отдельной отметке LTE дополнительно вызывается monitor-once. Проверка identity/resource не является криптографическим
  подтверждением физического устройства. Разделы читаются последовательно и
  не представляют собой атомарную картину состояния.
- При включённой опции приложение читает **журнал целиком** через `/log/print`
  или `GET /rest/log` в память, затем фильтрует его. Полный журнал может содержать
  пароли, адреса и другие частные данные; он не записывается в отчёт/файл этой
  функцией. Сетевой канал и устройство администратора должны быть доверенными:
  обычные API/HTTP могут передавать данные без шифрования, а имеющийся TLS-клиент
  не проверяет сертификат роутера. Другие поля обычного снимка, включая
  комментарии маршрутов, тоже могут содержать частную информацию.
- В историю возвращаются только фиксированные метки для строго распознанных
  строк и ограниченные числовые/логические значения; исходный текст сообщения,
  шлюз, адрес контрольной пробы, topics и другие поля не возвращаются. Время
  передаётся только в распознаваемом формате. Это минимизация данных, не гарантия
  безопасности всего отчёта: проверяйте его перед пересылкой.
- Показаны до 100 последних **по порядку ответа роутера** распознанных записей;
  при усечении показано предупреждение. Сортировка и интерпретация дат не
  выполняются. Время — строка роутера в его часовом поясе, иногда без даты;
  время сбора снимка отдельно указано в UTC. Неправильные часы роутера, перезапуск,
  очистка журнала, настройки логирования, старая версия скрипта или непризнанный
  формат могут скрыть события. Пустой список не доказывает, что переключений или
  ошибок не было. Записи с похожим текстом могут создавать и другие скрипты.
- Журнал читается после остальных разделов. Отказ доступа, недоступность меню,
  тайм-аут или превышение ограничений ответа отображаются как ошибка; при ошибке
  предыдущего чтения в API раздел будет помечен «не прочитано». Существующие
  лимиты API: 50 000 сообщений ответа / 64 МиБ; REST: 8 МиБ. При больших
  журналах чтение может не удаться; отсутствие частичных событий не означает,
  что журнал был пуст. Произвольные сетевые запросы и активные тесты не запускаются.

## Проверки

Тесты на имитациях API и REST проверяют opt-in, только читающие запросы, сверку
identity до журнала, пустой и ошибочный разделы, лимит, порядок, отбор событий,
отсутствие исходных сообщений/секретных полей, форматы времени и отмену показа
устаревшего результата в интерфейсе. Это не подтверждает поддержку каждой
версии RouterOS или фактического скрипта на конкретном роутере. Аппаратную
проверку выполнять только вместе с пользователем; рабочие WAN и резервирование
не меняются.
