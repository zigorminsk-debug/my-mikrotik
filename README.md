# MikroTik Inspector

Программа для **Windows**, **Linux/macOS** и **Android** с **HTML-интерфейсом**,
написанная на **Go** (Android-приложение — Go-ядро + WebView, см. раздел «Версия для Android»). Подключается к роутеру MikroTik (RouterOS) и показывает:

- 📌 **модель** устройства (board-name / routerboard),
- 📌 **версию прошивки** (RouterOS, текущая/заводская прошивка),
- 📌 **установленные пакеты** (имя, версия, статус).

И **конструктор конфигурации**: собирает готовый код для New Terminal под конкретную
модель и прошивку и умеет применять его на роутере одним нажатием.

Интерфейс — обычная HTML-страница: программа запускает локальный HTTP-сервер
(только `127.0.0.1`) и автоматически открывает её в браузере по умолчанию.
Пароль никуда не отправляется, кроме самого роутера.

## Возможности

| Функция | Описание |
|---|---|
| Два протокола | **RouterOS API** (бинарный, TCP 8728/8729) и **REST API** (HTTP/HTTPS, 80/443) |
| Режим «Авто» | Сначала пробуется API, при неудаче — REST; в ответе видно, какой протокол сработал |
| TLS | Поддержка HTTPS и API поверх TLS (самоподписанные сертификаты роутера) |
| Старые RouterOS | Вход и по одностадийной схеме (≥ 6.43), и по challenge-response (< 6.43) |
| Отчёт | Кнопка «Скопировать отчёт» — текстовая сводка в буфер обмена |
| **Конструктор** | Меню как в RouterOS: IP → Addresses/DHCP Server/DNS, System → NTP Client, PPP → PPPoE Client, Interface → Wireless; разделы включаются чекбоксами |
| **Учёт пакетов** | Если нужного пакета на роутере нет, поле неактивно и выводится надпись «необходимый пакет отсутствует» |
| **Приведение IP** | Поля адресов автоматически приводятся к формату IP (`192.168.001.010/024` → `192.168.1.10/24`) — и в браузере, и на сервере |
| **Применение** | Кнопки «Скопировать для New Terminal», «Применить на роутере», «Скачать .rsc» |
| **Android** | APK со встроенным Go-ядром: тот же интерфейс и конструктор на телефоне |
| **PWA** | Иконка и манифест: страницу можно добавить на домашний экран Android |
| Ноль зависимостей | Только стандартная библиотека Go |

## Сборка

Требуется Go **1.27+** (в `go.mod` зафиксирована версия, CI ставит её автоматически).

```bash
# Linux / macOS
go build -o mikrotik-inspector .

# Windows (из Windows)
go build -o mikrotik-inspector.exe .

# Кросс-сборка Windows-EXE из Linux
GOOS=windows GOARCH=amd64 go build -o mikrotik-inspector.exe .
```

Проверки перед пушем:

```bash
gofmt -l .        # должно быть пусто
go vet ./...
go test -race ./...
```

## Запуск

```bash
./mikrotik-inspector                # откроется браузер с интерфейсом
./mikrotik-inspector -no-browser    # не открывать браузер (печатает URL)
./mikrotik-inspector -addr 127.0.0.1:8099
./mikrotik-inspector -version
```

На Windows запустите `mikrotik-inspector.exe` двойным щелчком — откроется
консольное окно (логи) и страница интерфейса в браузере.

### Использование интерфейса

1. Введите адрес роутера (например `192.168.88.1`), логин и пароль.
2. Выберите протокол: **Авто** (рекомендуется), **RouterOS API** или **REST API**.
3. При необходимости укажите порт (`0` — по умолчанию) и отметьте **TLS/HTTPS**.
4. Нажмите **Подключиться** — появятся карточки устройства и таблица пакетов.

Порты по умолчанию:

| Протокол | Обычный | С TLS |
|---|---|---|
| RouterOS API | 8728 | 8729 |
| REST API | 80 | 443 |

> Для REST в RouterOS должен быть включён сервис `/ip service set www-ssl ssl-certificate=...`
> (или обычный `www`), для API — сервис `api`/`api-ssl`. Учётные данные администратора.

### Конструктор конфигурации

После подключения программа открывает вкладку **«Конструктор»**. Меню повторяет меню
RouterOS, а доступность пунктов зависит от данных устройства: модели, версии RouterOS,
установленных пакетов и сетевых интерфейсов.

| Пункт меню | Раздел | Что вводится | Почему может быть недоступен |
|---|---|---|---|
| `IP → Addresses` | адрес роутера в LAN | интерфейс, адрес с маской | пакет `system` |
| `IP → DHCP Server` | раздача адресов | интерфейс, пул (или авто), время аренды | пакет `dhcp` |
| `IP → DNS` | DNS-серверы | серверы через запятую, доступ из LAN | пакет `system` |
| `System → NTP Client` | точное время | серверы, часовой пояс | пакет `system` (NTP-клиент встроен) |
| `PPP → PPPoE Client` | интернет | WAN-интерфейс, логин, пароль, NAT | пакет `ppp` |
| `Interface → Wireless` | Wi-Fi | SSID, пароль (8–63), страна | пакет `wireless` / `wifiwave2` / `wifi-qcom` и наличие Wi-Fi-интерфейса |

Учитываются **объединённые сборки**: если на роутере установлен пакет `routeros`
(типично для RouterOS 7 и комбинированных сборок RouterOS 6), внутри которого уже есть
`system`, `dhcp`, `ppp` и поддержка радио, все разделы считаются доступными.

Если пакета нет, пункт показан неактивным с надписью
**«необходимый пакет отсутствует: <пакет>»**; для Wi-Fi при наличии пакета, но
отсутствии беспроводных интерфейсов — «на устройстве нет беспроводных интерфейсов».

Особенности:

- **Автоопределение режима Wi-Fi.** Для RouterOS 7 (`wifiwave2`, `wifi-qcom`, интерфейсы типа `wifi`)
  создаётся профиль `/interface wifi configuration` + привязка к интерфейсу; для legacy
  (`wireless`, `wlan*`) настройки применяются напрямую к интерфейсу.
- **Авторасчёт подсети.** Из адреса роутера вычисляются сеть, шлюз и пул DHCP
  (адрес роутера из пула исключается). Если поля пула пусты, подставляется автопул.
- **Приведение IP.** Уже при вводе в поля допускаются только цифры, точки, `/` и запятые,
  а по завершении ввода значение канонизируется (убираются ведущие нули, октеты > 255
  ограничиваются 255, маска — не больше 32). Сервер дополнительно нормализует значения
  перед валидацией, поэтому скрипт всегда содержит корректные адреса.
- **Идемпотентность.** Скрипт перед добавлением удаляет созданные ранее объекты
  (`remove [find comment=mti-lan]` и т.п.), поэтому его можно применять повторно.
- **Предпросмотр.** Скрипт пересобирается на сервере (`POST /api/config`) с задержкой
  ~220 мс после любого изменения и обновляется вместе с ошибками валидации.

Кнопки под предпросмотром:

| Кнопка | Действие |
|---|---|
| **Скопировать для New Terminal** | копирует скрипт в буфер обмена |
| **Скачать .rsc** | сохраняет файл `mikrotik-<модель>.rsc` |
| **Применить на роутере** | создаёт на роутере скрипт `mti-apply` с этим кодом и запускает его |

Применение идёт тем же подключением, что и чтение данных: по RouterOS API
(`/system/script/remove` → `/system/script/add` → `/system/script/run`) или по REST
(`POST /rest/system/script` → `POST /rest/system/script/run`). Результат тот же,
что при вставке кода в New Terminal. Перед изменениями рекомендуется
`/system backup save name=before-mti`.

> Ничего не применяется автоматически: кнопка «Применить» спрашивает подтверждение,
> а скрипт доступен для просмотра и ручной вставки.

## Версия для Android

Приложение для Android использует то же ядро, что и настольная версия, и тот же
HTML-интерфейс. Внутри процесса поднимается локальный HTTP-сервер
(`127.0.0.1:8765`), а системный WebView показывает страницу. Все обращения к роутеру
выполняет Go — интерфейс лишь отображает результат, поэтому мобильная версия
функционально не отличается от настольной (модель, прошивка, пакеты, конструктор,
применение настроек).

```
android/
├── bridge/bridge.go     # Go-ядро: Start/URL/Version/LocalURLs (gomobile bind)
├── app/                 # Java-обвязка: MainActivity с WebView, манифест, ресурсы
│   ├── build.gradle     # AGP 8.6.1, minSdk 21, targetSdk 34
│   └── src/main/java/com/mikrotik/inspector/MainActivity.java
├── tools.go             # удерживает golang.org/x/mobile в графе модуля
└── go.mod               # отдельный модуль, заменяет корневой через replace ../
```

### Установка на телефон

1. Скачайте `mikrotik-inspector-<версия>-android.apk` из
   [Releases](https://github.com/zigorminsk-debug/my-mikrotik/releases) или из
   артефакта `android-apk` запуска workflow «Android APK».
2. Разрешите установку из неизвестных источников (APK подписан отладочным ключом —
   этого достаточно для личного использования).
3. Телефон и роутер должны быть в одной сети (Wi-Fi роутера). Войдите под
   администратором; для API включите `/ip service set api` (8728), для REST —
   `/ip service set www` (80).

Приложение не требует root и не использует сторонние сервисы: пароль уходит
только на роутер.

### Что нужно знать

- **minSdk 21** (Android 5.0), поддерживаются ABI `arm`, `arm64`, `amd64`.
- Интерфейс адаптирован под узкий экран: вкладки, вертикальная раскладка
  «меню → предпросмотр», поля ввода с мобильной клавиатурой.
- Кнопка «Назад» работает как навигация внутри WebView.
- Дополнительно страницу можно открыть с компьютера: если запустить настольную
  версию с `-addr 0.0.0.0:8080`, в логах печатаются адреса вида
  `http://192.168.88.10:8080`.

### Как собирается APK

APK требует Android SDK, NDK, JDK и `gomobile`, поэтому собирается на GitHub
(workflow `.github/workflows/android.yml`, запускается автоматически при изменениях
в `android/`, `internal/`, `web/`, `mikrotik/` и по тегу `v*`):

```bash
# 1. Go-ядро → bridge.aar (на раннере уже есть SDK и NDK)
cd android && gomobile init
gomobile bind -target=android/arm,android/arm64,android/amd64 -androidapi 21 \
  -javapkg=com.mikrotik.inspector -o app/libs/bridge.aar \
  github.com/zigorminsk-debug/my-mikrotik/android/bridge

# 2. AAR + Java → APK
gradle -p . :app:assembleDebug -PappVersion=0.3.0 -PversionCode=3
# результат: android/app/build/outputs/apk/debug/app-debug.apk
```

Важные детали, на которых сборка спотыкалась (см. `docs/STEPS.md`, этап 3):

| Проблема | Решение |
|---|---|
| `gomobile: missing golang.org/x/mobile dependency` | `tools.go` + `go get golang.org/x/mobile@latest` в CI |
| Java не видит класс `Bridge` | `-javapkg=com.mikrotik.inspector` при `gomobile bind` |
| `resource mipmap/ic_launcher not found` | PNG-иконки в `res/mipmap-*` (генерируются Go-кодом) |
| нет NDK на раннере | шаг `sdkmanager --install "ndk;26.1.10909125"` |

Подпись релиза: если в секретах репозитория заданы `ANDROID_KEYSTORE_BASE64`,
`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, workflow
дополнительно собирает и подписывает release-APK; иначе публикуется debug-APK
(устанавливается на телефон).

```

├── main.go                    # точка входа настольной версии: сервер, открытие браузера
├── internal/server/           # общий HTTP-слой: API, иконки, манифест PWA
│   ├── server.go              # маршруты /api/*, заголовки безопасности, LocalURLs
│   └── icon.go                # генератор иконок (PNG без внешних зависимостей)
├── web/                       # интерфейс (встраивается в бинарник через embed)
│   ├── embed.go               # экспортирует встроенные файлы
│   └── index.html             # HTML/CSS/JS: вкладки «Информация» и «Конструктор»

│   ├── bridge/bridge.go       # Go-ядро для gomobile bind
│   ├── app/                   # Java-обвязка (WebView) + ресурсы + Gradle
├── mikrotik/
│   ├── proto.go               # кодек бинарного протокола RouterOS API (длина слова, предложения)
│   ├── api.go                 # клиент RouterOS API: вход (modern + challenge), чтение данных
│   ├── rest.go                # клиент REST API (Basic Auth, JSON)

│   ├── iface.go               # чтение интерфейсов (/interface/print и GET /rest/interface)
│   ├── apply.go               # применение скрипта на роутере (API и REST)
│   ├── mikrotik_test.go       # тесты сбора данных: кодек, mock API/REST, авторизация

├── .github/workflows/
│   ├── ci.yml                 # gofmt + vet + go test -race + проверка Android-кода + сборка Linux/Windows
│   ├── android.yml            # сборка APK (gomobile bind + Gradle), артефакт и Release
│   └── release.yml            # на тег v*: exe для Windows/Linux + GitHub Release с SHA256SUMS
├── docs/STEPS.md              # пошаговый журнал разработки
└── go.mod                     # модуль без внешних зависимостей
```

### Как это работает

1. `main.go` поднимает сервер на `127.0.0.1` и открывает `web/index.html`.
2. Интерфейс отправляет `POST /api/info` с параметрами подключения.
3. `mikrotik.Collect()` подключается к роутеру выбранным протоколом:
   - **API**: TCP-соединение, `/login`, затем `/system/identity/print`,
     `/system/resource/print`, `/system/routerboard/print`, `/system/package/print`;
   - **REST**: `GET /rest/system/identity|resource|routerboard|package` с Basic Auth.
4. Результат возвращается в JSON и отрисовывается в карточках и таблице.
5. Для конструктора интерфейс запрашивает `POST /api/interfaces` — сервер читает
   `/interface/print` (или `GET /rest/interface`) и возвращает интерфейсы вместе с
   доступностью разделов (`AnalyzeFeatures`).
6. Каждое изменение настроек отправляется на `POST /api/config`; сервер нормализует
   адреса, валидирует значения и возвращает готовый скрипт, вычисленные значения и
   список пропущенных разделов. Кнопка «Применить» вызывает `POST /api/apply`.

## Сборка на GitHub (GitHub Actions)

Сборка запускаются **на каждый push** — сразу после внесения изменений.

### CI (`.github/workflows/ci.yml`)

| Job | Что делает |
|---|---|
| `test` | `gofmt -l`, `go vet ./...`, `go test -race -count=1 ./...` |
| `build` | Сборка `linux/amd64` (ubuntu) и `windows/amd64` (windows-latest), загрузка артефактов |

Как посмотреть:

```bash
gh run list                 # список запусков
gh run watch                # следить за текущим запуском
gh run view --log           # логи последнего запуска
gh run download             # скачать собранные артефакты (exe)
```

Артефакты также доступны в UI: **Actions → запуск → Artifacts**.

### Android APK (`.github/workflows/android.yml`)

Запускается при изменениях в `android/`, `internal/`, `web/`, `mikrotik/`, по тегу `v*`
и вручную (`workflow_dispatch`). Собирает `bridge.aar` через `gomobile bind`, затем APK
через Gradle, публикует артефакт `android-apk` и (для тега) файл в GitHub Release.

```bash
gh run list --workflow="Android APK"        # история сборок APK
gh workflow run "Android APK"                # запустить вручную
```

### Релизы (`.github/workflows/release.yml`)

```bash
git tag v0.1.0
git push origin v0.1.0
```

На тег `v*` собираются `*-windows-amd64.exe` и `*-linux-amd64`,
создаётся GitHub Release с файлами и `SHA256SUMS.txt`.

## Тесты

```bash
go test -v ./mikrotik/
```

Покрыто:

- **чтение данных** — кодек длин/предложений, эталонный вектор challenge-авторизации,
  мок-сервер RouterOS API (современный вход, challenge-вход, неверный пароль),
  мок REST API (успех/401), fallback auto-режима, нормализация адресов
  (URL, `host:port`, IPv6), порты по умолчанию, недоступный хост;
- **конструктор** — расчёт сети/шлюза/пула (`/24`, `/30`, `/32`, IPv6, мусор),
  доступность разделов по пакетам и интерфейсам (DHCP, PPPoE, Wi-Fi legacy/wave2,
  объединённый пакет `routeros`, `wifi-qcom`),
  генерация скрипта для legacy и wave2, пропуск включённого недоступного раздела,
  ошибки валидации (CIDR без маски, пустой логин, короткий пароль Wi-Fi, пул вне
  подсети, DHCP без LAN), приведение IP-адресов, экранирование значений;
- **сеть** — чтение интерфейсов по API и REST, применение скрипта по API (порядок
  remove → add → run с игнорированием ошибки remove) и по REST (`{"number":"mti-apply"}`).

- **серверный слой** — отдача страницы, иконки PNG (декодирование и размеры),
  манифест PWA, коды ошибок `/api/*`, сквозной сценарий конструктора по HTTP,
  адреса локальной сети;
- **Go-ядро Android** — запуск сервера `bridge.StartOn`, отдача интерфейса и
  ответ `/api/config` (проверяется без телефона).

Всего 40+ тестов; интерфейс дополнительно проверяется сценарием на jsdom
(подключение → блокировка недоступного пункта → авторамат IP → предпросмотр → применение).
