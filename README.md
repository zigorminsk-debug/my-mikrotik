# MikroTik Inspector

Программа для **Windows**, **Linux/macOS** и **Android** с **HTML-интерфейсом**,
написанная на **Go** (Android-приложение — Go-ядро + WebView, см. раздел «Версия для Android»). Подключается к роутеру MikroTik (RouterOS) и показывает:

- 📌 **модель** устройства (board-name / routerboard),
- 📌 **версию прошивки** (RouterOS, текущая/заводская прошивка),
- 📌 **установленные пакеты** (имя, версия, статус).

И **конструктор конфигурации**: собирает готовый код для New Terminal под конкретную
модель и прошивку и умеет применять его на роутере одним нажатием.

Интерфейс — HTML-страница: программа запускает локальный HTTP-сервер
(по умолчанию только `127.0.0.1`). В Windows открывается отдельное окно
Microsoft Edge, в Linux/macOS — браузер по умолчанию.
Пароль никуда не отправляется, кроме самого роутера.

## Возможности

| Функция | Описание |
|---|---|
| Два протокола | **RouterOS API** (бинарный, TCP 8728/8729) и **REST API** (HTTP/HTTPS, 80/443) |
| Режим «Авто» | Сначала пробуется API, при неудаче — REST; в ответе видно, какой протокол сработал |
| TLS | Поддержка HTTPS и API поверх TLS (самоподписанные сертификаты роутера) |
| Старые RouterOS | Вход и по одностадийной схеме (≥ 6.43), и по challenge-response (< 6.43) |
| Отчёт | Кнопка «Скопировать отчёт» — текстовая сводка в буфер обмена |
| **Конструктор** | Меню как в RouterOS: IP → Addresses/DHCP Server/DNS, System → NTP Client, PPP → PPPoE Client, Interface → Wireless; разделы включаются чекбоксами |
| **Учёт пакетов** | Если нужного пакета на роутере нет, поле неактивно и выводится надпись «необходимый пакет отсутствует» |
| **Приведение IP** | Поля адресов автоматически приводятся к формату IP (`192.168.001.010/024` → `192.168.1.10/24`) — и в браузере, и на сервере |
| **Применение** | Кнопки «Скопировать для New Terminal», «Применить на роутере», «Скачать .rsc» |
| **Android** | APK со встроенным Go-ядром: тот же интерфейс и конструктор на телефоне |
| **PWA** | Иконка и манифест: страницу можно добавить на домашний экран Android |
| Ноль зависимостей | Только стандартная библиотека Go |

## Сборка

Требуется Go **1.27+** (в `go.mod` зафиксирована версия, CI ставит её автоматически).

```bash
# Linux / macOS
go build -o mikrotik-inspector .

# Windows (из Windows)
go build -ldflags "-H windowsgui" -o mikrotik-inspector.exe .

# Кросс-сборка Windows-EXE из Linux
GOOS=windows GOARCH=amd64 go build -ldflags "-H windowsgui" -o mikrotik-inspector.exe .
```

Проверки перед пушем:

```bash
gofmt -l .        # должно быть пусто
go vet ./...
go test -race ./...
```

## Запуск

```bash
./mikrotik-inspector                # откроется браузер с интерфейсом
./mikrotik-inspector -no-browser    # не открывать браузер (печатает URL)
./mikrotik-inspector -addr 127.0.0.1:8099
./mikrotik-inspector -version
```

На Windows установите setup или запустите портативный EXE: откроется отдельное
окно Microsoft Edge без консоли. Edge должен быть установлен. Пока программа
работает, в области уведомлений виден её значок: по правой кнопке — меню
«Открыть интерфейс» и «Выход». При закрытии окна приложение убирает значок,
останавливает локальный HTTP-сервер и завершается. Для каждого
запуска создаётся отдельный временный профиль Edge, чтобы не использовать фоновые
процессы обычного браузера; повторный запуск, пока окно открыто, блокируется.
Настройки, сохраняемые в localStorage, между такими сеансами не сохраняются.
Установщик перед записью файлов останавливает запущенный экземпляр
(`taskkill /IM MikroTikInspector.exe /F /T`), иначе Windows не даёт заменить
занятый exe и обновление поверх работающей копии падает с «Доступ запрещён».
Повторный запуск при живом значке показывает сообщение, где именно программа
уже работает.
Если окно Edge открылось, но страница в него не загрузилась (окно остаётся
пустым), программа замечает это по отсутствию обращений к локальному серверу,
показывает сообщение и открывает интерфейс в браузере по умолчанию.
Диагностический журнал: `%LOCALAPPDATA%\MikroTik Inspector\inspector.log`.
В нём записываются запуск и остановка окна, создание значка и локальный адрес,
но не пароли.
Ключи `-no-browser` и `-version` предназначены для консольной сборки; сборка с
`-H windowsgui` не показывает консоль.

### Использование интерфейса

1. Введите адрес роутера (например `192.168.88.1`), логин и пароль.
2. Выберите протокол: **Авто** (рекомендуется), **RouterOS API**, **REST API**.
   Значение **MAC-Telnet (по MAC)** выбирается само: как в WinBox, достаточно
   ввести MAC-адрес — список протоколов переключится на MAC-Telnet и станет
   недоступным для выбора; при вводе IP он снова разблокируется.
3. При необходимости укажите порт (`0` — по умолчанию) и отметьте **TLS/HTTPS**.
   Для MAC-подключения порт не используется.
4. Нажмите **Подключиться** — появятся карточки устройства и таблица пакетов.

Вместо IP-адреса в поле «Адрес роутера или MAC» можно указать MAC-адрес
устройства (например, `AA:BB:CC:DD:EE:FF`) — тогда Inspector подключится по
MAC (MAC-Telnet), как WinBox → Neighbors, без IP. Для этого компьютер должен
быть в том же L2-сегменте, что и роутер, а на роутере должен быть включён
MAC-Telnet/MAC-WinBox на разрешённых интерфейсах (`/tool mac-server`). Протокол
MAC-Telnet выбирается автоматически при вводе MAC-адреса.

Кнопка **«Подключиться к новому MikroTik»** сразу пробует `192.168.88.1`,
`admin` и пустой пароль, сбрасывая выбранный порт, протокол и TLS к значениям
по умолчанию. Это подключение по IP. Адрес доступен только если
устройство использует соответствующую заводскую конфигурацию, компьютер
подключён к её LAN-сегменту и на роутере включён API или REST. У некоторых
моделей начальный пароль указан на наклейке; после сброса без заводской
конфигурации IP-адреса может не быть. Если вход не удался, введите правильные
адрес и пароль вручную либо используйте WinBox. При отключённом TLS логин и
пароль передаются без защиты: используйте только доверенную локальную сеть.

Порты по умолчанию:

| Протокол | Обычный | С TLS |
|---|---|---|
| RouterOS API | 8728 | 8729 |
| REST API | 80 | 443 |

> Для REST в RouterOS должен быть включён сервис `/ip service set www-ssl ssl-certificate=...`
> (или обычный `www`), для API — сервис `api`/`api-ssl`. Учётные данные администратора.

### Конструктор конфигурации

После подключения программа открывает вкладку **«Конструктор»**. Меню повторяет меню
RouterOS, а доступность пунктов зависит от данных устройства: модели, версии RouterOS,
установленных пакетов и сетевых интерфейсов.

| Пункт меню | Раздел | Что вводится | Почему может быть недоступен |
|---|---|---|---|
| `IP → Addresses` | адрес роутера в LAN | интерфейс, адрес с маской | пакет `system` |
| `IP → DHCP Server` | раздача адресов | интерфейс, пул (или авто), время аренды | пакет `dhcp` |
| `IP → DNS` | DNS-серверы | серверы через запятую, доступ из LAN | пакет `system` |
| `System → NTP Client` | точное время | серверы, часовой пояс | пакет `system` (NTP-клиент встроен) |
| `PPP → PPPoE Client` | интернет | WAN-интерфейс, логин, пароль, NAT | пакет `ppp` |
| `Interface → Wireless` | Wi-Fi | SSID, пароль (8–63), страна | пакет `wireless` / `wifiwave2` / `wifi-qcom` и наличие Wi-Fi-интерфейса |

Учитываются **объединённые сборки**: если на роутере установлен пакет `routeros`
(типично для RouterOS 7 и комбинированных сборок RouterOS 6), внутри которого уже есть
`system`, `dhcp`, `ppp` и поддержка радио, все разделы считаются доступными.

Если пакета нет, пункт показан неактивным с надписью
**«необходимый пакет отсутствует: <пакет>»**; для Wi-Fi при наличии пакета, но
отсутствии беспроводных интерфейсов — «на устройстве нет беспроводных интерфейсов».

Особенности:

- **Автоопределение режима Wi-Fi.** Для RouterOS 7 (`wifiwave2`, `wifi-qcom`, интерфейсы типа `wifi`)
  создаётся профиль `/interface wifi configuration` + привязка к интерфейсу; для legacy
  (`wireless`, `wlan*`) настройки применяются напрямую к интерфейсу.
- **Авторасчёт подсети.** Из адреса роутера вычисляются сеть, шлюз и пул DHCP
  (адрес роутера из пула исключается). Если поля пула пусты, подставляется автопул.
- **Приведение IP.** Уже при вводе в поля допускаются только цифры, точки, `/` и запятые,
  а по завершении ввода значение канонизируется (убираются ведущие нули, октеты > 255
  ограничиваются 255, маска — не больше 32). Сервер дополнительно нормализует значения
  перед валидацией, поэтому скрипт всегда содержит корректные адреса.
- **Идемпотентность.** Скрипт перед добавлением удаляет созданные ранее объекты
  (`remove [find comment=mti-lan]` и т.п.), поэтому его можно применять повторно.
- **Предпросмотр.** Скрипт пересобирается на сервере (`POST /api/config`) с задержкой
  ~220 мс после любого изменения и обновляется вместе с ошибками валидации.

Кнопки под предпросмотром:

| Кнопка | Действие |
|---|---|
| **Скопировать для New Terminal** | копирует скрипт в буфер обмена |
| **Скачать .rsc** | сохраняет файл `mikrotik-<модель>.rsc` |
| **Применить на роутере** | создаёт на роутере скрипт `mti-apply` с этим кодом и запускает его |

Применение идёт тем же подключением, что и чтение данных: по RouterOS API
(`/system/script/remove` → `/system/script/add` → `/system/script/run`), по REST
(`POST /rest/system/script` → `POST /rest/system/script/run`) или, при
подключении по MAC, построчной отправкой команд в терминал роутера. Результат
тот же, что при вставке кода в New Terminal. Перед изменениями рекомендуется
`/system backup save name=before-mti`.

> Ничего не применяется автоматически: кнопка «Применить» спрашивает подтверждение,
> а скрипт доступен для просмотра и ручной вставки.

## Версия для Android

Приложение для Android использует то же ядро, что и настольная версия, и тот же
HTML-интерфейс. Внутри процесса поднимается локальный HTTP-сервер
(`127.0.0.1:8765`), а системный WebView показывает страницу. Все обращения к роутеру
выполняет Go — интерфейс лишь отображает результат, поэтому мобильная версия
функционально не отличается от настольной (модель, прошивка, пакеты, конструктор,
применение настроек).

```
android/
├── bridge/bridge.go     # Go-ядро: Start/URL/Version/LocalURLs (gomobile bind)
├── app/                 # Java-обвязка: MainActivity с WebView, манифест, ресурсы
│   ├── build.gradle     # AGP 8.6.1, minSdk 21, targetSdk 34
│   └── src/main/java/com/mikrotik/inspector/MainActivity.java
├── tools.go             # удерживает golang.org/x/mobile в графе модуля
└── go.mod               # отдельный модуль, заменяет корневой через replace ../
```

### Установка на телефон

1. Скачайте подписанный `mikrotik-inspector-<версия>-android-release.apk` из
   [Releases](https://github.com/zigorminsk-debug/my-mikrotik/releases), если он опубликован.
   Для тестирования доступен debug APK из артефакта `android-apk`; он может быть
   подписан другим ключом и не обновляться поверх себя.
2. Разрешите установку из неизвестных источников для выбранного приложения.
3. Телефон и роутер должны быть в одной сети (Wi-Fi роутера). Войдите под
   администратором; для API включите `/ip service set api` (8728), для REST —
   `/ip service set www` (80).

Приложение не требует root. Пароль роутера передаётся только роутеру;
проверка обновлений обращается к GitHub Releases.

### Что нужно знать

- **minSdk 21** (Android 5.0), поддерживаются ABI `arm`, `arm64`, `amd64`.
- Интерфейс адаптирован под узкий экран: вкладки, вертикальная раскладка
  «меню → предпросмотр», поля ввода с мобильной клавиатурой.
- Кнопка «Назад» работает как навигация внутри WebView.
- Дополнительно страницу можно открыть с компьютера: если запустить настольную
  версию с `-addr 0.0.0.0:8080`, в логах печатаются адреса вида
  `http://192.168.88.10:8080`.

### Как собирается APK

APK требует Android SDK, NDK, JDK и `gomobile`, поэтому собирается на GitHub
(workflow `.github/workflows/android.yml`, запускается автоматически при изменениях
в `android/`, `internal/`, `web/`, `mikrotik/` и по тегу `v*`):

```bash
# 1. Go-ядро → bridge.aar (на раннере уже есть SDK и NDK)
cd android && gomobile init
gomobile bind -target=android/arm,android/arm64,android/amd64 -androidapi 21 \
  -javapkg=com.mikrotik.inspector -o app/libs/bridge.aar \
  github.com/zigorminsk-debug/my-mikrotik/android/bridge

# 2. AAR + Java → APK
gradle -p . :app:assembleDebug -PappVersion=0.3.0 -PversionCode=3
# результат: android/app/build/outputs/apk/debug/app-debug.apk
```

Важные детали, на которых сборка спотыкалась (см. `docs/STEPS.md`, этап 3):

| Проблема | Решение |
|---|---|
| `gomobile: missing golang.org/x/mobile dependency` | `tools.go` + `go get golang.org/x/mobile@latest` в CI |
| Java не видит класс `Bridge` | `-javapkg=com.mikrotik.inspector` при `gomobile bind` |
| `resource mipmap/ic_launcher not found` | PNG-иконки в `res/mipmap-*` (генерируются Go-кодом) |
| нет NDK на раннере | шаг `sdkmanager --install "ndk;26.1.10909125"` |

Подпись релиза: если в секретах репозитория заданы `ANDROID_KEYSTORE_BASE64`,
`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, workflow
дополнительно собирает и подписывает release-APK; иначе публикуется debug-APK
(устанавливается на телефон).

### Как это работает

1. `main.go` поднимает сервер на `127.0.0.1` и открывает `web/index.html`.
2. Интерфейс отправляет `POST /api/info` с параметрами подключения.
3. `mikrotik.Collect()` подключается к роутеру выбранным протоколом:
   - **API**: TCP-соединение, `/login`, затем `/system/identity/print`,
     `/system/resource/print`, `/system/routerboard/print`, `/system/package/print`;
   - **REST**: `GET /rest/system/identity|resource|routerboard|package` с Basic Auth;
   - **MAC-Telnet**: UDP-пакеты на порт 20561 с MAC-адресами в заголовке,
     аутентификация EC-SRP5 (RouterOS 7.x) или legacy MD5, затем CLI-команды
     `:put [/path print as-value]` в терминале роутера.
4. Результат возвращается в JSON и отрисовывается в карточках и таблице.
5. Для конструктора интерфейс запрашивает `POST /api/interfaces` — сервер читает
   `/interface/print` (или `GET /rest/interface`) и возвращает интерфейсы вместе с
   доступностью разделов (`AnalyzeFeatures`).
6. Каждое изменение настроек отправляется на `POST /api/config`; сервер нормализует
   адреса, валидирует значения и возвращает готовый скрипт, вычисленные значения и
   список пропущенных разделов. Кнопка «Применить» вызывает `POST /api/apply`.

## Сборка на GitHub (GitHub Actions)

Сборка запускаются **на каждый push** — сразу после внесения изменений.

### CI (`.github/workflows/ci.yml`)

| Job | Что делает |
|---|---|
| `test` | `gofmt -l`, `go vet ./...`, `go test -race -count=1 ./...` |
| `build` | Сборка `linux/amd64` (ubuntu) и `windows/amd64` (windows-latest), загрузка артефактов |

Как посмотреть:

```bash
gh run list                 # список запусков
gh run watch                # следить за текущим запуском
gh run view --log           # логи последнего запуска
gh run download             # скачать собранные артефакты (exe)
```

Артефакты также доступны в UI: **Actions → запуск → Artifacts**.

### Android APK (`.github/workflows/android.yml`)

Запускается при изменениях в `android/`, `internal/`, `web/`, `mikrotik/`, по тегу `v*`
и вручную (`workflow_dispatch`). Собирает `bridge.aar` через `gomobile bind`, затем APK
через Gradle, публикует артефакт `android-apk` и (для тега) файл в GitHub Release.

```bash
gh run list --workflow="Android APK"        # история сборок APK
gh workflow run "Android APK"                # запустить вручную
```

### Релизы (`.github/workflows/release.yml`)

```bash
git tag v0.1.0
git push origin v0.1.0
```

На тег `v*` собираются `*-windows-amd64.exe` и `*-linux-amd64`,
создаётся GitHub Release с файлами и `SHA256SUMS.txt`.

## Тесты

```bash
go test -v ./mikrotik/
```

Покрыто:

- **чтение данных** — кодек длин/предложений, эталонный вектор challenge-авторизации,
  мок-сервер RouterOS API (современный вход, challenge-вход, неверный пароль),
  мок REST API (успех/401), fallback auto-режима, нормализация адресов
  (URL, `host:port`, IPv6), порты по умолчанию, недоступный хост;
- **конструктор** — расчёт сети/шлюза/пула (`/24`, `/30`, `/32`, IPv6, мусор),
  доступность разделов по пакетам и интерфейсам (DHCP, PPPoE, Wi-Fi legacy/wave2,
  объединённый пакет `routeros`, `wifi-qcom`),
  IPv4 WAN (DHCP/статический адрес/LTE, один или два канала с приоритетами),
  проброс портов (TCP/UDP, источник, внешний IP, hairpin NAT),
  генерация скрипта для legacy и wave2, пропуск включённого недоступного раздела,
  ошибки валидации (CIDR без маски, пустой логин, короткий пароль Wi-Fi, пул вне
  подсети, DHCP без LAN), приведение IP-адресов, экранирование значений;
- **сеть** — чтение интерфейсов по API и REST, применение скрипта по API (порядок
  remove → add → run с игнорированием ошибки remove) и по REST (`{"number":"mti-apply"}`).

- **серверный слой** — отдача страницы, иконки PNG (декодирование и размеры),
  манифест PWA, коды ошибок `/api/*`, сквозной сценарий конструктора по HTTP,
  адреса локальной сети;
- **Go-ядро Android** — запуск сервера `bridge.StartOn`, отдача интерфейса и
  ответ `/api/config` (проверяется без телефона).

Всего 40+ тестов; интерфейс дополнительно проверяется сценарием на jsdom
(подключение → блокировка недоступного пункта → авторамат IP → предпросмотр → применение).

### Интернет и проброс портов в конструкторе

Раздел **«Основной и резервный IPv4-каналы»** настраивает до двух провайдеров:
проводной (DHCP или статический IPv4) и LTE с собственным APN. У каждого канала
свой приоритет (distance) и необязательный NAT masquerade. Резервирование
(**контроль интернета**) работает только на RouterOS 7: ICMP роутера к
контрольному узлу закрепляется за основным каналом отдельной таблицей
маршрутизации, 30 секунд без ответа переводят трафик на резервный, 60 секунд
ответов — возвращают на основной. Проверка идёт раз в 5 секунд скриптом
`mti-failover`: три запроса за запуск, канал рабочий, если ответил хотя бы один
(одиночный ping на канале с потерями давал ложную аварию). Все шаги скрипт
пишет в журнал с префиксом `mti-failover:` — его показывает кнопка «Показать
журнал роутера (mti)».

Раздел **«Проброс портов и Hairpin NAT»** создаёт правила dstnat с комментариями
`mti-forward-*`: внешний порт, протокол, локальный адрес и порт сервера,
необязательные внешний IP и разрешённый источник, hairpin для доступа из LAN по
внешнему адресу. Порядок правил и разрешение dstnat в цепочке forward
проверяются вручную: firewall конструктор не меняет.

Ограничения и состояние остальных разделов — в
[плане конструктора](docs/CONSTRUCTOR-ROADMAP.md). Перед применением сделайте
backup/export и проверьте существующие DHCP-клиенты, адреса и маршруты.

### VPN в конструкторе

В разделе **VPN** доступны WireGuard (отдельно для MikroTik-сервера и
MikroTik-клиента), а также клиенты OpenVPN и PPTP. WireGuard требует RouterOS 7
и настраивается **в два прохода**: приватный ключ создаёт сам роутер, вводить
его не нужно.

1. **Шаг 1 — поднять интерфейс.** Укажите адрес интерфейса с маской и локальный
   UDP-порт. Скрипт создаёт интерфейс `mti-wg-*` (RouterOS сам генерирует пару
   ключей), назначает адрес, выводит публичный ключ и сохраняет его в
   комментарии интерфейса. Ключ появляется в разделе после нажатия
   «Обновить данные устройства» — его же можно прочитать командой
   `/interface wireguard print detail`.
2. **Шаг 2 — добавить peer.** Передайте полученный ключ другой стороне, вернитесь
   в раздел, переключитесь на шаг 2 и укажите публичный ключ другой стороны и
   сети туннеля (allowed-address). Клиенту нужны также адрес и UDP-порт
   сервера. Интерфейс, порт и адрес вводить повторно не нужно.

Локальный UDP-порт на каждой стороне и порт сервера в клиенте можно изменить;
порт сервера в клиенте должен совпадать с локальным портом сервера. WireGuard
работает только по UDP. Настройте обе стороны согласованно; сервер поддерживает
одного peer в создаваемом интерфейсе. Повторное применение шага 1 не меняет
ключи уже существующего интерфейса.

Профиль OpenVPN требует RouterOS 7.7 или новее, поддерживает выбор TCP или UDP и порта сервера и использует IP, AES-256-CBC и SHA1 с проверкой сертификата сервера:
заранее импортируйте доверенный CA и, если сервер требует, клиентский сертификат
с закрытым ключом. Протокол и порт должны совпадать с настройками сервера, который также должен поддерживать эти параметры. PPTP устарел и
небезопасен — предпочтителен WireGuard. Маршруты, доступ через firewall,
проброс порта и NAT, кроме выбранного маршрута по умолчанию OpenVPN, конструктор не настраивает; при необходимости настройте их
вручную на обеих сторонах. VPN-разделы создают новые интерфейсы с именами
`mti-*` и не удаляют существующие: перед повторным применением удалите ранее
созданный интерфейс вручную. Скрипт содержит ключи и пароли — храните его безопасно.

#### Выпуск сертификатов OpenVPN

Раздел **VPN → OpenVPN — выпуск сертификатов** запускается на серверном
MikroTik с RouterOS 7 после настройки времени. Укажите DNS-имя или IP,
по которому клиент обращается к серверу, имя клиента и пароль экспорта.
Скрипт создаёт новый CA `mti-ovpn-ca`, серверный `mti-ovpn-server` и один
клиентский `mti-ovpn-client`, а затем экспортирует публичный CA в PEM и
клиентский сертификат с закрытым ключом в защищённый паролем PKCS12. Серверный
ключ и ключ CA остаются на сервере. Файлы находятся в **Files**; передайте CA
и PKCS12 клиенту защищённым каналом, затем удалите PKCS12 с сервера и после
импорта — с клиента. Храните пароль и скрипт отдельно и безопасно: скрипт,
в том числе служебный скрипт применения на роутере, содержит пароль экспорта.

На клиенте импортируйте CA как доверенный и PKCS12 с паролем; в разделе
OpenVPN-клиента укажите имя импортированного клиентского сертификата. На сервере
в настройках OpenVPN укажите `mti-ovpn-server` и настройте сервер, PPP-учётные
записи, firewall и маршруты отдельно — выпуск сертификатов их не создаёт.
Скрипт не переиспользует существующий CA и останавливается, если сертификаты
с именами `mti-ovpn-*` уже существуют; не удаляйте действующий CA ради
повторного запуска, иначе прежние сертификаты потеряют доверие. Для выпуска
дополнительных клиентских сертификатов используйте существующий CA вручную.


#### Маршрут и профиль OpenVPN-клиента

В OpenVPN-клиенте выберите выход через **локальный шлюз** или **сервер VPN**.
Скрипт блокирует маршруты, навязываемые сервером (`route-nopull=yes`); при
выборе VPN включает автоматический маршрут по умолчанию. Маршруты к удалённым
сетям необходимо добавить вручную. Убедитесь, что маршрут VPN имеет приоритет
перед существующим WAN-маршрутом: одинаковые distance могут привести к ECMP.
При отключении VPN возможен выход через WAN — это не kill switch. Проверьте
также маршрут до адреса сервера, DNS, IPv6, настройки firewall и NAT на сервере.

Кнопка **«Скачать профиль клиента .ovpn»** формирует в браузере профиль для
OpenVPN 2.6+ из полей клиента. Укажите CA в PEM (.crt) и, если сервер требует
сертификат клиента, PKCS12 (.p12/.pfx), экспортированные с сервера. Для проверки
подлинности сервера укажите точный CN его сертификата, если он отличается от
адреса подключения. Файл содержит логин и пароль открытым текстом, а при выборе
PKCS12 — и защищённый ключ клиента; пароль PKCS12 вводится при подключении.
Скачивание и передачу файла следует выполнять только в доверенной среде и по
защищённому каналу. Профиль не создаёт сервер или учётную запись; они должны
быть настроены отдельно. Внешний клиент блокирует маршруты, переданные сервером;
при выборе VPN добавляется `redirect-gateway def1`, для локального выхода
маршруты к сетям VPN настраиваются вручную. Не все приложения OpenVPN
поддерживают встроенные логин/пароль и PKCS12; профиль рассчитан на OpenVPN 2.6+.

### Защита WAN и управление через WinBox

Раздел **Безопасность → Защита извне — только WinBox** формирует отдельный
скрипт; остальные разделы конструктора перед этим нужно выключить. Выберите
**все** реальные внешние интерфейсы (не более трёх; доверенных адресов или подсетей — не более четырёх), через которые приходят IP-пакеты (при
PPPoE — в том числе PPPoE-интерфейс), и перечислите доверенные IPv4-адреса
или сети для WinBox, включая свой текущий адрес и сеть администрирования LAN.
Выберите TCP-порт WinBox. Широкое разрешение `0.0.0.0/0` не принимается.

На выбранных WAN правила помещаются в начало цепочки `input`: разрешены
WinBox из доверенных адресов, существующие и связанные соединения, DHCP-клиент,
а при наличии IPv6 — ICMPv6 и DHCPv6; остальные входящие соединения к роутеру
блокируются. Для WinBox на всех интерфейсах задаётся список доверенных IPv4.
Telnet, FTP, SSH, WebFig/REST, API/API-SSL, MAC-Telnet, MAC-WinBox, обнаружение
соседей, bandwidth-server, proxy, SOCKS и UPnP отключаются. Приложение после
этого не сможет подключиться через API/REST, пока их не включат вручную.

**Осторожно:** правила не защищают невыбранные WAN и не меняют цепочку
`forward`, пробросы портов и доступ к устройствам за роутером. Они блокируют
новые входящие VPN на выбранных WAN; текущие установленные соединения могут
продолжать работать. IPv6 WinBox не разрешён. Ручные правила могут потребоваться
для VPN и других служб. Скрипт не обновляет RouterOS, не проверяет пароли и не
заменяет аудит существующей конфигурации. Проверьте IPv6 и применимость правил
к вашей топологии. Не запускайте его повторно при наличии правил `mti-sec-*`.

Сохраните резервную копию, убедитесь в доступе к физической консоли и запустите
скрипт вручную через WinBox New Terminal с **Safe Mode**, чтобы при потере
сеанса изменения откатились. Кнопка удалённого применения для этого раздела
отключена намеренно. Прежде чем завершить Safe Mode, проверьте новый WinBox-сеанс
с доверенного адреса и работу интернета.


### Обновления Android

При запуске приложение проверяет последние стабильные GitHub Releases не чаще
раза в сутки; кнопка **«Проверить обновления»** запускает проверку вручную.
При наличии обновления пользователь подтверждает скачивание и установку через
системный установщик Android. На Android 8+ может потребоваться разрешить
установку из этого источника. Тихая установка без подтверждения не выполняется.

Обновление принимает только `android-release.apk` с соответствующей суммой
SHA-256 и подписью, совпадающей с установленным приложением; проверяются имя
пакета и увеличение versionCode. APK с другой подписью не устанавливается.
Для работоспособности обновлений каждый релиз должен подписываться одним и тем
же постоянным release-ключом и публиковать `SHA256SUMS-android.txt`. В GitHub
Actions нужны секреты `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`; без них подписанный APK не
публикуется, и проверка сообщит, что он недоступен. Debug-APK из Actions может
иметь другой ключ и не обновляется release-APK поверх себя. Переход на другую
подпись может потребовать удаления старой версии и потери её локальных данных.

Установщик Windows собирается при публикации тега в GitHub Actions с помощью
Inno Setup 6; результат и его SHA-256 добавляются в Release. Проверочная сборка
установщика также сохраняется как артефакт Windows CI. Сборки не подписаны
цифровой подписью Windows, поэтому SmartScreen может показать предупреждение.
Ярлык на рабочем столе установщик создаёт по желанию (галочка в конце
установки); ярлык в меню «Пуск» создаётся всегда. Иконка приложения не хранится
в репозитории: перед сборкой установщика её генерирует `go run ./tools/makeicon`
в `windows/app.ico` из той же процедурной отрисовки, что отдаёт `/icon.png`.
Её же использует значок в области уведомлений, а ярлыки и запись в «Программы
и компоненты» берут иконку из установленного `app.ico`. Сам `MikroTikInspector.exe`
иконки не содержит: у Go-сборки без ресурса Windows она не встраивается.

### Белый список для ресурса за NAT

Раздел **«Доступ к ресурсам за NAT»** ограничивает один уже настроенный dst-nat
ресурс по IPv4. Выключите остальные разделы, укажите уникальный идентификатор,
внешний интерфейс, **внутренний** адрес и порт после трансляции и TCP или UDP.
Затем выберите до 12 стран и нажмите «Загрузить IP выбранных стран», и/или
укажите отдельные IPv4-адреса и CIDR (до 1000 вручную). Максимум — 60 000
суммарных префиксов. Загрузку стран можно не выполнять при использовании
только отдельных адресов. Если выбор стран изменился, загрузите данные заново.

Страны загружаются по HTTPS из [ipverse/country-ip-blocks](https://github.com/ipverse/country-ip-blocks)
(данные делегирования RIR, CC0-1.0). Это **не точная геолокация**: адреса
операторов, мобильных сетей, CDN, VPN и прокси могут находиться не там, где
указано делегирование. Источник требует интернет-соединения и может ограничивать
число запросов; ошибки загрузки не подменяются пустым списком. Данные в памяти
приложения кэшируются до 12 часов; отображается время их получения. Списки на
роутере автоматически не обновляются: для обновления заново загрузите сети,
сгенерируйте и импортируйте скрипт с тем же идентификатором ресурса.

Скрипт создаёт отдельный address-list и два правила в начале `forward`, прежде
чем удалить предыдущие созданные им правила и списки для того же идентификатора.
Для совпадающего dst-nat и выбранного WAN доверенный источник явно разрешается,
остальные блокируются. **Правило разрешения стоит выше существующего firewall**;
проверьте соответствие вашей политике. Скрипт не создаёт dst-nat и не защищает
другие порты, протоколы, внешние интерфейсы, соединения без dst-nat или IPv6.
Все пробросы на выбранный внутренний адрес и порт через данный WAN подпадают
под правило независимо от внешнего адреса и порта.
Для каждого другого набора используйте отдельный идентификатор; не создавайте
пересекающиеся правила для одного и того же ресурса. Уже работающие и FastTrack
соединения могут обходить новую проверку до окончания conntrack — проверяйте
доступ с новых соединений и при необходимости очищайте соответствующие записи
вручную. Определение страны не заменяет авторизацию и TLS на самом сервисе.

Перед импортом сохраните резервную копию и обеспечьте локальный доступ. Кнопка
«Применить» для этого раздела отключена: скачайте полный `.rsc`, перенесите его
на роутер и выполните `/import file-name=...` из локального терминала. В окне
может отображаться сокращённый предпросмотр. Большие списки могут потребовать
значительных памяти и времени; Safe Mode не подходит для тысяч изменений.
Повторный импорт **того же файла** останавливается: для обновления сгенерируйте
новый скрипт. Проверяйте работу после импорта; при прерывании могут остаться
частично созданные служебные записи `mti-nat-*`.

### Поиск соседей и резервное копирование

Кнопка «Найти MikroTik в сети» отправляет MNDP-запрос по UDP 5678 и слушает
ответы около трёх секунд. Нужны один L2-сегмент, включённое обнаружение на
роутере и разрешённый UDP 5678 в брандмауэре; изоляция Wi-Fi, VPN, несколько
адаптеров, занятый порт или ограничения Android могут помешать поиску. MNDP
не аутентифицирован, сведения могут быть поддельными. Кнопки выбора подставляют
IP или MAC найденного соседа: по IP подключение идёт через API/REST, по MAC —
через MAC-Telnet (аналогично WinBox → Neighbors), и конструктор работает в обоих
случаях. MAC-подключение требует того же L2-сегмента и включённого
MAC-Telnet/MAC-WinBox на роутере; оно не работает через VPN и маршрутизаторы.

Раздел «Бэкап по расписанию» создаёт binary backup и отправляет его одному
получателю. SMTP-сервер, порт, режим шифрования, отправителя, логин и пароль
приложения скрипт передаёт прямо в команду `/tool e-mail send`, поэтому
настраивать `/tool e-mail` на роутере не нужно — именно из-за ненастроенного
`/tool e-mail` письма чаще всего и не уходят: команда отправки падает, не
оставляя записи в журнале. Имя сервера разбирается командой `:resolve`, значит
на роутере должен работать DNS (или укажите IP сразу). Полный TLS (SMTPS, порт
465) доступен с RouterOS 7.13, на более старых версиях используйте STARTTLS
(порт 587). Каждый шаг задания пишет в журнал —
`/log print where message~"mti"`: по нему видно, создался ли файл и ушло ли
письмо. Те же строки показывает кнопка «Показать журнал роутера (mti)» в
разделе — она читает журнал по API или REST (по MAC-Telnet журнал недоступен). Интернет, DNS, время и часовой пояс должны работать: без точного времени
планировщик сработает не тогда, когда вы ждёте. Один файл
`mti-scheduled.backup` перед очередным запуском удаляется и заменяется новым,
в том числе при ошибке создания или отправки; храните независимые копии.
Повторное применение заменяет одноимённые скрипт и расписание. Пароль SMTP и
пароль шифрования содержатся в сгенерированном скрипте и сохраняются на роутере,
а при применении через API также в служебном `mti-apply`; ограничьте доступ и
сохраните пароли отдельно. Если пароль шифрования не указан, бэкап создаётся
открытым (`dont-encrypt=yes`). Тестов на реальном RouterOS и SMTP-сервере не
проводилось, совместимость настроек SMTP зависит от версии RouterOS.
